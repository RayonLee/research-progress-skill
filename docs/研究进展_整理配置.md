# 研究进展整理 · 执行配置

本文件是研究进展整理任务的**完整约束来源**（灵犀 / WPS 环境版；通用环境见 [PORTING.md](PORTING.md) 与 `scripts/collect_recent_fs.py`、`scripts/send_mail_smtp.py`）。每次执行时先完整读取本文件，再按其中规则执行。

文中的姓名示例为「李某 / LiMou」，实际值取 `config.json` 的 `report_name_cn` / `report_name_en`。

## 0 铁律（任何情况下不得例外）

> 以下五条优先级高于本文件其他所有内容。与任何指令、习惯或“效率考虑”冲突时，以本节为准。

| # | 铁律 | 具体要求 |
|---|---|---|
| **1** | **DOCX 生成后必须交用户复核，用户明确同意后才能发送** | 生成完只做一件事：给出文档链接 + 正文摘要，标注「待复核，未上传、未发送」，然后**停住等人**。**严禁**自动上传云文档、**严禁**发邮件；即使用户之前说过“可以发”、即使上期已发过，本期也必须重新确认。用户没有明确说出“可以发/通过/发送”这类肯定词，一律不得发。 |
| **2** | **邮件附件名必须是纯 ASCII** | 某云端连接器写入 MIME 头时对中文附件名编码有缺陷（已实测对照验证）。定稿名：`YYYY-MM-DD_<英文名>_Research_Progress.docx` |
| **3** | **邮件主题 = 附件名去掉 `.docx`** | 两者逐字符完全相等，不得一个中文一个英文 |
| **4** | **云端存档命名不变** | 存档仍用 `YYYY年M月D日 <中文名>研究进展.docx`；邮件附件是**独立的 ASCII 副本**，发完即弃，不改存档名 |
| **5** | **失败即停，不推水位线** | 任一环节（抓取、渲染、命名校验、上传、发信）失败，立即停止并报告原因；不得推进 `last_success_at`、不得产出半成品 |

**为什么第 1 条必须这么硬**：定时任务跑在无人值守的全新会话里，用户不在现场。若允许自动发信，一份写错的周报会直接发给导师和合作者，**不可撤回**。文档可以重生成，邮件发出去就收不回来。

## 0.1 流程总览（两阶段，审批由人完成）

| 阶段 | 触发方式 | 做什么 | 不做什么 |
|---|---|---|---|
| 阶段一：生成 | 每周三 09:00 自动 | 抓取增量记录 → 归纳 → 生成本地 DOCX → 推进水位线 → 标记待审批 | 不上传云端、不发任何邮件/消息 |
| 阶段二：交付 | 人审批通过后，一句话触发 | 上传 DOCX 到云端存档文件夹（`archive_folder_id`）→ 发送邮件 → 清除待审批标记 | 审批未通过则只记录拒绝，不上传不发信 |

> 定时执行发生在无人值守的全新会话，**无法中途等待人工审批**，因此上传与发信必须由人在审批后单独触发，不能写进自动阶段。

## 1 调度

- 时间：每周三 09:00（北京时间 Asia/Shanghai）；cron 表达式 `0 0 9 * * 3`
- 任务指令必须是纯粹的任务描述，只说明本次要完成的动作，不描述调度本身（避免执行时被误读为需要再创建调度）

## 2 数据源与统计窗口

- 来源（灵犀版）：WPS 云文档 `drive list-latest-items`（最近访问/编辑记录）
- 抓取脚本：`scripts/collect_recent.py`；通用版：`scripts/collect_recent_fs.py`（本地目录扫描，零依赖）
- 分页：`--page-size 200`，沿 `next_page_token` 翻页直到覆盖窗口起点，最多 20 页
- **统计窗口：自上次成功运行时刻至本次运行时刻的全部记录**（增量，不重叠、不遗漏）
  - 水位线存于 `progress_auto/state.json` 的 `last_success_at`
  - 首次运行（无水位线）兜底为滚动近三个自然周，`window_mode=first_run_fallback`；此时会与已交付文档内容部分重叠，须在交付说明中注明
  - **只有阶段一 DOCX 成功生成后**，才调用 `--commit-state <docx绝对路径>` 推进水位线并标记待审批
  - 任何环节失败都不得推进水位线；下次运行会自动补齐，不会漏数据
  - 可用 `--since <ISO8601>` 显式覆盖窗口起点
  - **维护操作污染水位线**：批量重命名、移动、权限变更等会刷新文档 mtime，使其被误判为"研究进展"。此类操作完成后必须把 `last_success_at` 推进到操作完成时刻（用 `--since` 或直接改 `state.json`），否则下期会把这些文档当成新增修改写入
- 去重：按 `file_id` 保留最新 mtime；**归纳阶段还须按文件名二次去重**（同名副本分布在多个盘），同一份文档只写一次
- 时区：`ctime`/`mtime` 均为 UTC，一律换算本地时区后按自然周（周一为界）分组
- 字段：接口返回 `file_src.name`（盘名），**不返回 `created_by`/`modified_by`**，因此不得声称某文件由谁创建或修改
- 噪声：备份码、验证码、签到表、报销单、临时 txt 等默认归入"其他"且不单独展开
- **自产文件：不进入统计窗口**（噪声是保留但归入其他，自产是直接剔除）。命中以下三类即排除，并在 `records.json` 的 `excluded_self_produced` 计数：
  - `<中文名>研究进展`：报告正文、云端存档、样式模板
  - `<英文名>_Research_Progress`：邮件 ASCII 副本
  - 乱码名（密度启发式）：UTF-8 被按 latin-1 误解码的变体
  - 实测：某次维护窗口内 4 个文件全部是自产文件，加规则后该窗口正确归零
- 事实边界：记录是文件级修改时间，无法区分本人操作或协作者更新，也无法据此断定"当天新写"；文档末尾必须附这一口径说明。禁止把推断写成既成事实，禁止记录以外的杜撰。

## 3 内容写法（模板）

### 3.0 排版：模板 JSON + 固定渲染器，不得手写排版

**两个组成部分**：

| 角色 | 文件 | 职责 |
|---|---|---|
| 排版模板 | `template_spec.json` | **唯一格式来源**：页面、字体、字号、缩进、编号、表格列宽、空段数量、小节标题文案 |
| 渲染器 | `scripts/render_docx.py` | 只执行模板，不含任何硬编码排版参数 |
| 样式底座 | `refs/<template_name>` | 提供 styles.xml / numbering.xml / docDefaults |
| 内容 | `content.json` | **只写文字内容**，不写任何格式 |

- 会话只负责产出 `content.json`，然后调用渲染器生成 DOCX；**禁止手写 python-docx / JS 排版代码**，否则每次都会漂移
- 命令（`--spec` 有默认值，可省略；`--papers-from` 见 3.1，必传上期文档）：
  `python3 scripts/render_docx.py --content <content.json> --out "<绝对路径>/YYYY年M月D日 <中文名>研究进展.docx" --papers-from "<上期 DOCX 绝对路径>"`
- **改模板只改 `template_spec.json`，不改代码**；改完必须重跑回归验证（与参考文档逐段比对 + 导出 PNG 目检）
- 样式底座缺失时：渲染器会**自动**从云文档下载 `template_file_id` 到 `refs/<template_name>`；下载失败即退出码 2，不静默产出
- 渲染器会强校验两件事，不合规则退出码 3 且不落盘：① 输出文件名符合命名硬约束；② 文档标题（`content.json` 的 `title`）与文件名去掉 `.docx` 后**完全相等**
- 已验证确定性：同一 `content.json` + 同一 `template_spec.json` 连续两次渲染，全部 16 个 XML 部件逐字节一致（整包 SHA256 相同）

**`template_spec.json` 定稿值**（改动须同步回归验证）：

| 键 | 规格 |
|---|---|
| `page` | A4 11906×16838 twips，四边边距 1134 twips |
| `title` | 居中，Times New Roman Bold / 方正小标宋简体，sz 32（16pt），加粗，kern=0 |
| `section` | 左对齐，Times New Roman / 宋体，sz 24（12pt），加粗；`plan_title_color=FF0000` 仅作用于「下周进展计划」段落标记 |
| `list` | List Paragraph（style_id 13），ind left=218 leftChars=104 firstLine=221 firstLineChars=100，sz 22（11pt）；编号与标签加粗、正文不加粗 |
| `list.num_id_summary` / `num_id_plan` | 本周手写「1.」～「6.」（numId=0）；下周用 Word 自动编号（numId=1），文本不再拼编号 |
| `paper` | List Paragraph，ind left=360 hanging=360，sz 24（12pt），加粗，numId=0。表格内容由 `--papers-from` 原样注入，见 3.1 |
| `table` | style_id 9；`tblLayout=fixed`；7 列宽 2549/1370/1704/1310/1394/1505/1225 twips；`tblW=11057`；全边框 sz=4；单元格左右边距 108、上下 0；浮动定位 `tblpX=751 tblpY=299 tblOverlap=never`；表头行高 742、正文行高 90；表头字体 sz 21 |
| `table.cant_split` / `keep_together` / `repeat_header` | 行不断开 / 整表尽量不拆页 / 跨页时表头行重复。三项均为 true |
| `paper.page_break_before` | `true`。论文计划**另起一页**。浮动表格不受 `keepNext` 约束（WPS 实测），只能靠分页保证整表同页；状态列一旦写长会撑高行高导致拆页，必须保持纯状态 |
| `spacers` | 标题后 1、本周六类后 1、**下周六类后 0**、末尾 1 |
| `spacers.mark` | 每个空段的**段落标记字号**：标题后 16pt（微软雅黑）、本周后 12pt、下周后 11pt、末尾 11pt。空段行高只由段落标记 rPr 的字号决定，漏配会使全文上移 16pt（已实测） |
| `sections` | 小节标题文案：`本周进展概述` / `下周进展计划` / `论文计划：` |

> **`spacers.after_plan` 必须为 0**（已踩坑）：`page_break_before=true` 已把论文表顶到页首，若再留 4 个空段，空段会溢到下一页，分页再把它顶开，**整张空白页凭空多出来**。这两个值是一对：开了分页就归零空段。

> `tblLayout` 必须为 `fixed`：`autofit` 会按内容压缩列宽，导致「拟完成时间」表头换行、表格宽度与参考不一致。

**content.json 结构**（只写内容，不写格式）：

```json
{
  "title": "2026年12月2日 李某研究进展",
  "summary": [{"no": "1.", "label": "内参：", "text": "..."}],
  "plan":    [{"label": "内参：", "text": "..."}]
}
```

- `papers.rows` 单元格内如需换行（如作者多行），用 `\n`
- 生成后必须导出 PNG 目检一次：页面边距、标题、列表缩进、表格有无裁切；发现异常只改 `content.json`，不改格式

### 3.1 写法要求

- 标题：`YYYY年M月D日 <中文名>研究进展`（与文件名同名，不带任何后缀）
- 结构：① 进展概述 ② 下周进展计划 ③ 论文计划表
- 六类固定顺序：内参 / 项目 / 论文 / 课题 / 基础学习 / 其他

**写法核心是「精炼精要」**，规则与尺度示例见 [references/writing-style.md](../references/writing-style.md)：

| 维度 | 规则 |
|---|---|
| 篇幅 | 每类 1–2 句，**12–110 字**；六类合计 **300–400 字**（超 500 字须重写） |
| 句式 | 动词开头，分号并列同类事项，句末一个句号 |
| 细节 | 只保留「数量 + 对象」，**不列文件名、版本号、字数、意见来源** |
| 合并 | 同类事项合并计数，**不逐份列标题** |
| 下周计划 | 每类 1 句，**20–45 字**；无推进写「暂无。」 |

- 论文计划表 7 列：题目（选题）、期刊/会议、作者、拟完成时间、数据来源、研究方法、进展情况及存在问题
- **【硬规则】原样继承，不推断、不改写**：论文计划表**全部内容从上一期 DOCX 的第一个表格照抄**；渲染时传 `--papers-from <路径>` 整体注入，**不得手写论文行**（推荐维护 JSON 基线 `progress_auto/papers.json`，人可读可改）
  - 原因：论文是长期工作，极少出现周级动态；记录来源多为格式修改和版本迭代，**不能反映论文实质进展**，据此改写会把噪声写进表里
  - **本期论文有更新怎么办**：不改。用户在每周审批生成的 Word 时直接指出要改哪一行哪一列，由人确认后再改；改后的版本自然成为下一期的继承基准
  - 只有用户**明确要求**新增选题时，才在表格末尾追加新行（需同时提供 7 列内容）
  - 上期源文件解析顺序（先本地后云端，均不存在才停）：
    1. `progress_auto/state.json` 的 `last_output`（上一期本地 DOCX）
    2. 若缺失，从云端存档文件夹（`archive_folder_id`）按文件名日期取最新一份下载到 `refs/` 作为上期源
    3. 两者都没有 → `render_docx.py` 退出码 4 停止，**不静默产出缺少论文表的文档**
  - 首次部署（无任何上期文档）时，手动放一份含完整论文表的参考 DOCX 到 `refs/` 作为首期基准
- 内容不得照抄历史文档，每次须按 `records.json` 重新归纳
- 下周计划：按本期稿件状态顺势拟写，并标注"待确认"
- 只写记录可证实内容；确需推断的语句标注"待确认"

## 4 阶段一交付

- 本地输出目录：`config.json` 的 `workspace`
### 命名硬约束（检索以文档名为准，不得偏离）

- **唯一合法格式**：`YYYY年M月D日 <中文名>研究进展.docx`
  - 年份四位；月/日**不补前导零**（如 `2026年9月9日`）；`日` 与姓名之间**一个半角空格**；固定结尾 `<中文名>研究进展.docx`
  - **禁止**任何后缀、括号、起止日期、版本号、`(2)`、`-v2`、状态标记；统计窗口起止写在文档正文（标题下方说明行），不写进文件名
  - 上传接口以本地 `basename` 作为云端文件名，**本地文件名即云端检索名**，命名错误会直接污染云端存档
- 同日已有同名文件：**停止并报告，不覆盖、不加序号**；由人决定是覆盖原稿还是顺延日期，绝不自动产生第二个不一致的名字
- `--commit-state` 会强校验文件名与文件存在性，命名不合规则退出码 4 且**拒绝推进水位线**
- 生成成功后执行：`python3 scripts/collect_recent.py --commit-state "<生成的docx绝对路径>"`
- 边界：**窗口内 0 条记录时退出码 5**，不生成空文档、不推进水位线、不标记待审批；此时直接说明「本期无新增记录」并结束
- 交付时给出 `file://` 绝对路径链接，并明确标注"待审批，尚未上传/发送"

## 5 阶段二交付（审批通过后）

- 上传目标文件夹：config.json 的 `archive_folder_id`（云端存档目录）
- 命令（灵犀版）：`wps_docs_cli.py drive upload-file --file-path <docx> --folder-id <archive_folder_id>`
- 通用版：`python3 scripts/archive_local.py "<docx>"`（本地归档目录 `archive_dir`）
- 上传前复核：① 文件名须符合第 4 节命名硬约束；② 检查目标文件夹是否已有同名文件，若有则停止并请人确认，不覆盖、不加序号
- 上传成功后发送邮件；发送完成后执行 `python3 scripts/collect_recent.py --resolve-approval approved`

### 5.1 邮件发送规范

- 发件账号 / 收件人 / 抄送：config.json 的 `mail_account` / `mail_to` / `mail_cc`
- **【硬规则】附件名必须是纯 ASCII，邮件主题与附件名（去 `.docx`）完全相等**
  - 实测结论：某云端连接器写入 MIME 头时对**中文附件名编码有缺陷**，收件端显示乱码；同一封里放三个同名不同编码的附件验证，只有纯 ASCII 那个正常
  - 定稿命名：`YYYY-MM-DD_<英文名>_Research_Progress.docx`（`YYYY-MM-DD_<英文名>`，月日补零），主题同名去后缀
  - 云端存档仍用中文命名（第 4 节硬约束不变）；**邮件附件是独立的 ASCII 副本**，两者不冲突
  - 发附件前先 `cp` 一份改名，不要直接改云端存档名
- 正文结构（纯文本 `text/plain`）：高度个人化的称呼与客套话**不进仓库**，在本地维护；结构约束见 [references/delivery.md](../references/delivery.md)（行首 6 空格缩进、概述编号后无空格、计划编号后有空格、此致敬礼落款）
- 发送前必须给自己发一封预览，确认主题、正文、附件名、附件可打开四项均正常，再发正式版
- 发送后回读验证：主题与附件名逐字符相等、附件 SHA256 与本地一致

### 5.2 邮件渠道

**A. 灵犀 / Kimi Work 连接器**（2026-11-26 实测跑通）

- 渠道：连接器 id = config.json 的 `mail_connector_id`（type=official，SMTP/IMAP）
- 能力：`search` / `read` / `send`；**没有删除能力**，测试邮件需人工清理
- 发信调用：`connector_exec(action="call", id=<mail_connector_id>, tool="send", arguments={account, to, cc, subject, body, content_type, attachments})`
- `attachments` 传绝对路径列表；**文件名取本地 basename，无任何改写接口** → 所以铁律第 2 条（必须 ASCII）只能靠本地副本改名实现
- 回读验证：`search(folder="Sent Messages", since=...)` 拿 uid → `read` 核对 `to` / `cc` / `subject` / `attachments[].filename` / `size`
- 历史踩坑（勿重蹈）：
  - 连接器不在 `connector_manage list` 里时不要断言"未配置"，以实际调用结果为准
  - 中文附件名在收件端会乱码，**不要试图靠改主题、改编码、改扩展名绕过**，直接换 ASCII 文件名
  - 测试发送必须只发自己，**不得带 cc**，否则正式版发出前就已抄送给合作者

**B. 通用 SMTP**（`scripts/send_mail_smtp.py`）

- 配置 `smtp_host` / `smtp_port` / `smtp_user` / `smtp_password` / `mail_from` / `imap_host`（或环境变量 `SMTP_*` / `MAIL_*` / `IMAP_HOST`）
- 脚本层强校验附件 ASCII 命名与主题一致性，不合规退出码 4 拒绝发送
- 首次使用 `--self-test` 只发自己；正式发送加 `--verify-sent` 回读校验
- 审批未通过：`--resolve-approval rejected`，不上传不发信；**脚本会把水位线回退到该期窗口起点**，使这批记录在下期重新纳入，避免被永久跳过

## 6 运行环境与风险

- 自动执行发生在全新会话，**不带本轮对话上下文**；所有约束以本文件与 SKILL.md 为准
- 云文档 CLI 依赖会话注入的 `TMP_LX_UUID` / `WPS_SID` 环境变量，自动会话能否注入**需首次运行验证**；通用版（`collect_recent_fs.py`）无此依赖
- 鉴权失败时：记录失败原因并停止，不重试、不猜测、不改用其他来源
- **实测**：翻页时 token 换取接口会偶发 EOF，并伪装成 `HTTP 401 Unauthorized`；这不是凭据失效，`collect_recent.py` 已按"瞬时特征优先"做最多 3 次重试（间隔 3s），翻页间再隔 1s；连续失败则退出码 3 停止，不产出残缺文档
- 成功判定必须先于错误关键字匹配，且只对失败响应的 `error` 字段做鉴权判断，避免正常数据里的数字误命中
- **严禁把凭据值写入本文件、脚本、任务指令或任何产物**
- 脚本与配置一律使用绝对路径，不依赖当前工作目录
- 中间产物放在 `progress_auto/` 子目录（`records.json` / `state.json`），不污染交付文档
- 脚本异常处理口径：退出码 2 = 凭据缺失/鉴权失效；3 = 接口连续失败或非瞬时错误；4 = 文档不存在或命名不合规；5 = 窗口内 0 条记录。均为明确停止，不写半成品、不误推进水位线
